# Ключи для жюри: инструкция и проверка

Основание — актуальная [инструкция организаторов о шифровании](https://docs.ostrovok.tech/s/b9e6ec5e-5ad6-4091-9c85-a48eee9b21cc/doc/shifrovanie-sekretov-klyuchej-6Qhc4gJOPZ), проверена 28 октября 2026 года по Москве. Для LLM требуется **отдельный ключ для жюри**; его передают в бинарном файле `secrets.env.age` в корне репозитория, в сдаваемой ветке/теге. `.env` и ключи открытым текстом в Git, чат или почту не отправляют.

## Текущее состояние команды

- Публичный ключ организаторов в инструкции: `age1932fu7f70rwyfhaxflyfszz4gf6avxwc95wc0yjwm6zns9tspycqpgdnc0`. Перед финальным шифрованием ещё раз сверить его с оригиналом.
- Личный бесплатный ключ GigaChat пользователя предназначен для личного тестирования; его [условия](https://developers.sber.ru/docs/ru/policies/gigachat-agreement/individuals) запрещают передавать учётные данные третьим лицам в Freemium. Шифрование не отменяет это ограничение. Доступный **отдельный разрешённый ключ для жюри пока не подтверждён**.
- Для проб друга нужен его собственный разрешённый доступ либо отдельно согласованный командный сервис. Зашифрованный только для организаторов файл он расшифровать не сможет — публичный ключ предназначен не для этого.
- `.env`, `.env.jury` и другие `.env.*` исключены из Git; `.env.example` остаётся отслеживаемым и содержит перечисленные переменные без значений. Пустые параметры конфигурации заменяются документированными безопасными настройками по умолчанию.
- По просьбе владельца текущий личный `.env` дополнительно зашифрован публичным ключом организаторов в локальный файл **вне репозитория**. Он не передан и не является сдаваемым: инструкция организаторов требует отдельный ключ, а условия личного доступа ограничивают передачу. Организаторская расшифровка не проверена.
- **Сдаваемый `secrets.env.age` ещё не создан и не опубликован.** Это нельзя отмечать как готовую передачу жюри, пока нет подходящего отдельного ключа и проверки его работоспособности.

## Проверка без настоящего секрета

На нашем компьютере загружен официальный `age` 1.3.2; SHA-256 архива проверен по метаданным релиза. `tools/verify_age_workflow.py` создаёт только вымышленный образец и временную тестовую пару ключей, затем проверяет бинарный формат, шифрование на публичный ключ организаторов, невозможность расшифровки случайным ключом и полное шифрование/расшифровку на временной паре. Реальные `.env` и секреты он не читает.

```bash
python tools/verify_age_workflow.py
# Если age установлен не в PATH:
python tools/verify_age_workflow.py --age-dir <папка-с-age-и-age-keygen>
```

Проверка прошла локально на вымышленных данных. Отдельно реальный личный `.env` зашифрован только локально; проверены бинарный формат и отсутствие открытого значения ключа в файле. У нас нет закрытого ключа организаторов: расшифровку ими, итоговый доступ жюри и работоспособность будущего отдельного ключа эти проверки **не подтверждают**. Скрипт не создаёт сдаваемый `secrets.env.age`.

## Когда появится разрешённый отдельный ключ

1. Проверить условия поставщика, доступные модель и квоту, ограничения и отдельное назначение ключа для жюри. Выбрать правильные `LLM_PROVIDER`, `LLM_MODEL` и при необходимости `GIGACHAT_SCOPE` в зависимости от конкретного аккаунта; не выдумывать доступ.
2. Локально подготовить полный конфигурационный файл, например `.env.jury`, в UTF-8 без BOM; одна переменная `NAME=value` на строку, без лишних кавычек и пробелов. Пример имён и настройки по умолчанию — в `.env.example` и README. Это отдельный файл, чтобы не заменить личные настройки пользователя.
3. Установить официальный [age](https://github.com/FiloSottile/age/releases) и сверить актуальный публичный ключ из инструкции. Из корня репозитория выполнить шифрование именно этого файла:

```bash
age -r age1932fu7f70rwyfhaxflyfszz4gf6avxwc95wc0yjwm6zns9tspycqpgdnc0 -o secrets.env.age .env.jury
```

Файл `.env.jury` содержит те же значения, которые организаторы после расшифровки поместят в `.env`; имя исходного локального файла не меняет формат результата. Организаторы в примере используют исходник `.env`. Не применять `-a`, перенаправление `>` или конвейер `|`: по инструкции нужен бинарный файл, записанный через `-o`. При изменении содержимого зашифровать заново.

4. Локально проверить на **разрешённом** ключе подключение к модели и тестовые фразы без ПДн, отсутствие лишних открытых файлов в индексе и историю публикации. Не печатать ключ в терминал или отчёт. Команда `git ls-files .env .env.jury` не должна выдавать имена.
5. Добавить `secrets.env.age` в корень **сдаваемой** ветки/тега, описать провайдер, модель и запуск в README. До этого момента не коммитить вымышленный образец как будто это действующий ключ.

Если ключ был закоммичен открытым текстом, его нужно считать скомпрометированным и перевыпустить: удаление файла из последнего коммита не удаляет значение из истории. Сообщение в `/help` оформляется без ключей и содержимого файла.
