# Ответы через LLM: RAG и маскирование

Ответ пользователю пишет языковая модель, но только по фактам, которые посчитал код, и по найденным фрагментам путеводителей. Модель не видит исходных личных данных. Каждый её ответ проверяется перед показом.

## Цепочка одной реплики

```
реплика
 → маскирование: «Меня зовут Иван, +7 916 …» → «Меня зовут [имя_1], [телефон_1]»   (core/guard.py, core/privacy.py)
 → понимание: LLM + правила → сверка (arbiter)                                    (core/agent.py)
 → шаг домена: факты (варианты, цены, рейсы, вопросы) — их считает код           (domains/trips/domain.py)
 → RAG: фрагменты путеводителя по направлению и теме вопроса                       (domains/trips/guides.py)
 → генерация: модель пишет ответ только по фактам и фрагментам                    (core/answer.py)
 → проверка ответа: числа, цены, варианты, ссылки, контакты, метки, обещания
     не прошла → одна повторная попытка → шаблон
 → метки → имена (только имена) → пользователю
```

Так устроены корпоративные решения: Salesforce Einstein Trust Layer (grounding, masking, zero retention, demasking), Microsoft Presidio с обратимой анонимизацией, LLM Guard (Anonymize → Vault → Deanonymize).

## Маскирование

- Распознавание локальное: регулярные выражения (телефоны, почта, карты, паспорта, СНИЛС, адреса, коды, IP, номера брони, сведения о здоровье) и NER Natasha для имён. Внешних сервисов нет.
- Метки обратимые и с типом: `[имя_1]`, `[телефон_1]`. Одно значение в разговоре — одна метка, «Иван» после «Иван Петров» — тот же `[имя_1]`. Модель видит структуру фразы, но не данные.
- Таблица «метка → значение» (`Vault`) живёт только в памяти сессии. В модель, историю диалога и логи она не попадает.
- В ответ пользователю возвращаются только имена. Номера карт, документов и контакты не повторяются, вместо них остаётся `[телефон]`.
- Если после маскирования остались признаки чувствительных данных или фильтр не сработал, текст в модель не уходит, отвечают правила.
- Проверка: `eval/answers_live.py` перехватывает все запросы к модели и ищет в них исходные значения. На 62 запросах тестовых диалогов утечек нет.

## RAG по путеводителям

- **База знаний** — `domains/trips/data/guides.json`: статьи Wikivoyage (ru, при отсутствии — en) по 75 направлениям, 2 759 фрагментов по ~700 символов. У фрагмента есть направление, раздел, тег раздела (`see`, `areas`, `eat`, `safety`, `transport`, `arrive`…), ссылка. Пересборка: `make guides` (`tools/build_guides.py`). Лицензия текстов CC BY-SA 4.0, источник подписывается в ответе.
- **Поиск** — локально, в процессе приложения:
  - BM25 по основам слов (лёгкий стеммер: «Будве» = «Будва»);
  - смысловое сходство по векторам слов navec, которые входят в Natasha;
  - фильтр по метаданным: только выбранное направление и профильные разделы (на вопрос о районах не отвечает раздел «Безопасность», даже если там есть слово «район»);
  - бонус первому абзацу раздела, обычно обзорному.
- **Где используется:**
  - вопросы о месте («что посмотреть», «какой район», «где поесть», «безопасно ли», «как передвигаться») — ответ по путеводителю с источником; такие вопросы не меняют условия поездки;
  - вопросы о визе, погоде, дороге — фрагменты профильных разделов идут модели как контекст;
  - идеи направлений и варианты поездки — краткое «о месте», чтобы модель рассказала живее.
- Без модели вопрос о месте всё равно получает ответ: первые предложения найденного фрагмента с источником. Если в путеводителе ответа нет, агент так и говорит.

## Проверка ответа модели (`core/answer.py`)

Ответ не показывается, если:

| Проверка | Пример |
| :--- | :--- |
| число не из фактов, источников или реплики | «всего 88 500 ₽», хотя в фактах 98 500 |
| потеряна цена или номер варианта | из трёх вариантов осталось два |
| потерян вопрос к пользователю | факты заканчиваются вопросом, ответ — нет |
| ссылка или контакт | «подробнее на booking.com» |
| метка, которой не было | `[имя_2]`, когда пользователь назвал одно имя |
| обещание, которого нет в фактах | «я уже забронировал» |
| ответ не на русском, пустой или слишком длинный | — |

После отказа — одна повторная попытка с перечнем замечаний, затем шаблон. Шаблон построен кодом из тех же фактов и всегда верен.

## Модель и контур

Провайдер задаётся в `.env`: GigaChat (сервис в РФ), любой OpenAI-совместимый API или своя модель в контуре (`LLM_PROVIDER=local`, `LLM_BASE_URL` — vLLM, Ollama, llama.cpp). Цепочка одинакова для всех. Маскирование нужно и для GigaChat: стороннему сервису отдаём минимум данных. `LLM_NLG=0` выключает генерацию, тогда ответы только шаблонные.

## Проверка

- `make test` — автономные тесты, в том числе `tests/test_rag_answers.py`: метки, отсутствие личных данных в запросах, проверка ответа, повтор и шаблон, поиск по путеводителю, ответ на вопрос о месте без модели и с моделью.
- `make answers` — живой прогон 7 диалогов с моделью: доля ответов модели, причины отказа проверки, задержка, утечки. Отчёт — `eval/answers_report.md`.
