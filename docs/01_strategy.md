# 01. Стратегия

## Подход: управляемый агент

LLM разбирает запрос путешественника в структуру (город, даты, гости, бюджет, звёзды, удобства, расположение, цель поездки). Поиск, ранжирование и текст ответа делает детерминированный код.

```
запрос → guard → LLM: извлечь изменения параметров (JSON по Pydantic-схеме)
       → слияние с состоянием диалога → логика домена:
            не хватает города?   → уточняющий вопрос
            данных достаточно?  → поиск → ранжирование → ответ с объяснением выбора
       → (опционально) LLM перефразирует ответ, используя только факты
```

Почему так:
- **Демо не ломается.** Если LLM недоступна или вернула мусор, агент всё равно отвечает осмысленно.
- **Нельзя выдумать отель или цену.** Всё берётся из каталога.
- **Объяснимость.** Причины выбора («рейтинг 9.1, 1 км от центра, есть завтрак») считает код.
- **Тестируемость.** Поиск и ранжирование покрыты тестами без LLM.

## Как раскрыть «остальное устроит агент»

Минимальный запрос — сразу результат, без анкеты. Над базовым поиском стоит строить:
1. **Работу с отзывами**: почему этот отель подходит именно под запрос («тихо», «с детьми», «рядом с метро»).
2. **Агентный слой**: агент сам планирует поездку — даты, сравнение вариантов, «что рядом», бюджет на всю поездку.
3. **Уточнения в диалоге**: «а ближе к центру?», «а подешевле?» без потери контекста.
4. **Пустой результат не тупик**: ослабляем фильтры и говорим, что именно ослабили.

## Чем выигрываем

1. Отрепетированное демо из 3–4 запросов, включая сложный: «ничего не нашлось — вот лучшее, что есть, и почему».
2. Метрики: точность разбора запроса, доля запросов, решённых с первого сообщения, задержка ответа.
3. Бизнес-упаковка: меньше шагов до бронирования, выше конверсия поиска, персонализация по отзывам.
4. Устойчивость: промпт-инъекции, офтоп, смена параметров на лету, неполные данные.
