# 01. Стратегия: как решаем оба хакатона

## Выбор кейса «Точки сборки»

| Критерий | DBI (голосовая запись в клинику) | М.Видео (нормализация характеристик) | GigaCowork (генерация курсов) |
| :--- | :--- | :--- | :--- |
| Синергия с Островком | **Высокая.** Диалог, slot-filling, поиск по каталогу (слоты ↔ отели), уточнения, альтернативы при пустом результате | Средняя. Извлечение и нормализация пригодятся для разбора атрибутов и отзывов отелей, но это батч-задача без диалога | Низкая. Генерация контента — другая задача |
| Wow-эффект на демо | Высокий: живой голосовой звонок | Средний: таблица до и после плюс метрики | Средний |
| Объективная метрика | % успешных записей, время диалога, WER | Точность и полнота по атрибутам (легко посчитать) | Субъективная |
| Риски | STT/TTS, задержка, медицинская чувствительность, формат API МИС | Качество разметки и объём категорий | Размытые критерии |

**Рекомендация: DBI.** Код ядра (диалог, извлечение, policy, поиск с ослаблением фильтров, интерфейсы) переиспользуется почти целиком. Голос добавляется отдельным слоем поверх текстового ядра.
**План Б: М.Видео.** Берём его, если в команде некому заниматься голосом или если в данных DBI окажется сложная интеграция.

## Подход: «управляемый агент» вместо свободного агента

Схема работы: LLM разбирает реплику (NLU) и при желании переформулирует ответ (NLG), а решения принимает детерминированный Python.

```
реплика → guard → LLM: извлечь изменения параметров (JSON по Pydantic-схеме)
        → merge с состоянием диалога → policy домена (Python):
             не хватает данных?  → уточняющий вопрос
             данных достаточно?  → поиск или запись → ответ по шаблону
        → (опционально) LLM перефразирует ответ, используя только факты
```

Почему так:
- **Демо не ломается.** У каждого LLM-шага есть детерминированный fallback. Если LLM недоступна или вернула мусор, бот всё равно отвечает осмысленно.
- **Работает на открытых моделях Cloud.ru.** Извлечение JSON надёжнее, чем многошаговый function calling на моделях среднего размера.
- **Тестируемость.** Policy и поиск покрываются юнит-тестами без LLM. Качество извлечения меряем отдельным eval-набором.
- **Объяснимость.** Причины выбора отеля или слота считаются кодом, поэтому ответ не может их выдумать. Жюри это любит.

Свободный tool-calling агент («что посмотреть рядом с отелем», «сравни два варианта») добавляем вторым слоем, если останется время. В трек Островка «агент делает всё остальное» он хорошо ложится как wow-фича.

## Чем выигрываем

1. **Отрепетированный сценарий демо** из 3–4 диалогов, включая сложный кейс: нет мест или нет отелей, бот предлагает альтернативы и объясняет почему.
2. **Метрики на слайде:** точность извлечения на eval-наборе, доля диалогов, дошедших до записи или выбора, медианная задержка ответа.
3. **Бизнес-упаковка:**
   - DBI: снижение нагрузки на колл-центр, работа 24/7, меньше пропущенных звонков и выше конверсия в запись.
   - Островок: меньше шагов до бронирования, выше конверсия поиска и персонализация на основе отзывов.
4. **Edge cases:** промпт-инъекции, офтоп, смена параметров на лету, неполные данные.
5. **Безопасность в медицине:** не ставим диагнозов, жалобы только маршрутизируем к специалисту, показываем дисклеймер.
